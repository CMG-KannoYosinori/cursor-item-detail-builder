# 商品概要コーディング

`docs/coding-workflow.md` のワークフロー定義に従うこと。作業前に次も読む。

- `docs/project-workflow.md`
- `docs/css-architecture.md`

特に次を厳守する。

1. 「ヒアリング項目」の5つの質問を、この順番で1つずつ（またはまとめてでもよいが省略はしない）ユーザーに尋ねる。作業ディレクトリ・スマホ/PCデザインカンプのファイルパス・画像アセットのファイルパス・フッター注意文言（単一選択、選択肢は「不要」を含む5択）・アコーディオンUIを使うか、のすべての回答が揃うまで、コーディングを開始しない。デザインカンプ・画像アセットともチャット添付ではなくファイルパスを聞く（理由はそれぞれ後述）。
2. 対象ディレクトリ（例: `15066html/`）が存在しない場合は、ディレクトリ名からプロジェクト ID を読み取り、`docs/project-workflow.md` の手順（`00000html/` を複製 → `00000` を一括置換 → `dist/00000.html` をリネーム）をエージェントが自ら実行して作成する。ユーザーに手作業を案内するのではなく代行する。置換時は `(?<!\d)00000(?!\d)` のように前後が数字でない場合のみ置換し、商品 URL 等の無関係な数字列を壊さないこと。既に存在するが `00000` のまま未置換の場合も同様に置換を実施する。`00000html/` 自体は複製元として変更しない。
3. 実装対象は対象ディレクトリの `dist/{id}.html` 内、`<!-- 商品概要 -->` と `<!--//商品概要 -->` の間のみ。加えてヒアリングしたフッター注意文言の選択を `.pjt--common` 内の該当ブロックへ反映する（選んだ1つだけ残し他は削除、「不要」なら全削除）。それ以外の範囲は指示がない限り変更しない。
4. CSS の追加は `docs/css-architecture.md` の区分に従う（`dist/styles/style.css` を直接編集し、使い回せる UI は `Blocks` セクション、この案件だけの組み立ては `Pages — project` セクション）。クラス命名規則・ブレークポイントは `00000html/` の実装（`max-width: 640px` のモバイルファースト、`pc:` プレフィックス）を参照する。
   - デザインカンプは2倍解像度で提出される（PC 1280px / SP 750px）。SP（`@media (width >= 640px)` の外側）はカンプ（750px）上の測定値をそのまま `calc(値 / 750 * 100vw)` の形でフルード実装する。PC（`@media (width >= 640px)` 内）はカンプ（1280px）上の測定値を2で割った実測 px でピクセルパーフェクトに実装し、SP でフルード化した全プロパティを上書きする。詳細は `docs/css-architecture.md` の「SP のフルードスケーリング」を参照。
   - 数値・色は目分量で決めない。デザインカンプのファイルパスから、Bash 上の画像処理スクリプト（Python の Pillow、`ImageMagick` の `convert`/`identify` 等）を使って指定座標のピクセル色（hex 値）や要素の境界・余白をピクセル単位で実測してから CSS に反映する。画像に「Multiply coordinates by X」のような実寸換算の倍率が示されている場合はそれも使えるが、スクリプトによる実測を優先する。
   - `00000html/` を複製した直後の `Blocks` / `Pages — project` セクションには見本用のダミー値（色・余白・フォントサイズ等）が入っている。これをそのまま残さず、今回のデザインカンプの実測値に置き換える。特に配色をテンプレートのまま残さない。
   - デザインカンプと実装結果に差が出た場合、CMS 側の共通 CSS（jQuery Mobile / Bootstrap スコープ / reset / properties / main / layout / module / style--*.css。変更不可）の影響も疑い、ブラウザの開発者ツールで Computed スタイルを確認する。影響がある場合は `.p{id}` 配下に詳細度の高い上書きを `Foundation` セクションへ追加する（前例: `.bootstrap-v3-3-7--scope .p{id} a:focus`）。詳細は `docs/coding-workflow.md` の「デザインカンプ再現の精度を上げるルール」を参照。
5. アコーディオンUIの回答が「使う」なら `p{id}-accordion-details` のマークアップと `accordion.2.js` の `<script>` タグ（ローカル/CDN 切り替えコメント付き）を含める。「使わない」なら両方とも含めない。
6. 画像アセットは、ユーザーから伝えられたファイルパスから `dist/images/` へコピー・リネームして配置する（既存の命名パターン `{id}-{名前}[--pc|--sp][.バージョン].{拡張子}` に合わせる）。チャットに貼られた画像はテキストとしてしか書き出せず、エージェントはそこから直接ファイルを生成できないため、ファイルパスを聞かずに済ませない。SP/PC で画像を出し分ける場合は `<img>` の切り替えではなく `<picture>`（`<source media="(min-width: 640px)">` + フォールバック `<img>`）を使う。デザインカンプ画像自体はファイルパスを計測に使うのみで、`dist/images/` に置いたりリポジトリにコミットしたりしない。
7. アコーディオンの設置場所(何を開閉式にするか)や、ボタン・バナーのリンク先 URL がデザインカンプ・添付情報だけでは判断できない場合は、事前ヒアリングを待たず実装中にその都度ユーザーへ質問する。仮の値で憶測して埋めない。
8. 実装後は SP/PC 双方の見た目を Live Server で確認するようユーザーに促す（ビルド・監視ステップはないため、保存すれば即反映される）。PC は 640px 幅でピクセル単位の一致を、SP は 320px〜640px の複数幅でフルードスケーリングが破綻していないかを確認してもらう。
