# 商品概要コーディングワークフロー

デザインカンプと画像アセットをもとに、Cursor Agent が商品詳細ページの HTML/CSS をコーディングするための対話フロー。HTML 初心者のチームメンバーが安心して使えるよう、必ず決まった質問から会話を始める。

## 起動方法

Agent チャットで `/coding` を実行して起動する（定義: `.cursor/skills/coding/SKILL.md`）。スキルは明示呼び出し専用なので、自然文だけでは起動しない。

キーワード検知（例: チャットに「コーディングして」と書いたら自動で始まる、など）は採用しない。理由:

- `/coding` は入力時に補完候補として出てくるため、初心者でも見つけやすい。
- キーワード検知は自然文中の意図しない一致で誤発火したり、逆に言い回しが違うと反応しなかったりする。
- ヒアリング項目が固定されているタスクなので、コマンドとして明示的に呼び出す方が「何を聞かれるか」が事前に分かり親切。

チャット内で「コーディングして」等と自然文で話しかけられた場合は、エージェント側から `/coding` の利用を案内する（推測でヒアリングを省略して進めない）。

## ヒアリング項目

`/coding` が起動したら、必ず次の順番で質問し、回答が揃うまで実装に進まない。

1. 作業するディレクトリを教えてください（例: `15066html/`。新規案件でまだ存在しない場合は、そのディレクトリ名からプロジェクト ID を読み取り、`00000html/` を複製して作成する）
2. スマホ用とPC用のデザインカンプのファイルパスを教えてください（Photoshop などからの書き出しファイルを想定。PC は 1280px、スマホは 750px の2倍解像度で作成したものを想定。詳細は「デザインカンプの仕様」参照）。チャットへの添付ではなく、あらかじめ PC 上の任意の場所にファイルとして保存しておいてもらい、そのパスを共有してもらう（理由は「デザインカンプの受け渡しと計測」参照）
3. 画像アセットのファイルパスを教えてください（`{id}html/dist/images/` に配置する納品用の画像）。あらかじめ PC 上の任意の場所にファイルとして保存しておいてもらい、そのパスを共有してもらう（詳細は「画像アセットの受け渡し」参照）
4. フッターの注意文言を選択してください（単一選択）
   - 送料関係費に関するご注意: 通常
   - 送料関係費に関するご注意: 沖縄以外
   - クール便配送の重要事項: 冷凍便
   - クール便配送の重要事項: 冷蔵便
   - 不要
5. アコーディオンUIを使いますか？（原材料名・栄養成分などの開閉表示）

対象ディレクトリが存在しない・プロジェクト ID 置換がまだの場合は、@project-workflow.md の手順（`00000html/` の複製・置換・リネーム）をエージェントが自ら実行してから次に進む。ユーザーに手作業を案内するのではなく、エージェントが代行する。

## 実装中に確認する項目

次の内容は事前のヒアリングには含めず、実装を進める中でデザインカンプ・添付情報だけでは判断できない場合にその都度ユーザーへ質問する。

- **アコーディオンの設置場所**: アコーディオンUIを使う場合でも、ページ内のどこに配置するか（原材料名・栄養成分など何を開閉式にするか）がデザインカンプから読み取れない場合は、実装中に尋ねる。
- **ボタン・バナーのリンク先 URL**: `p{id}-button` や `p{id}-banner__item` などのリンク先 URL がデザインカンプや添付情報から分からない場合は、実装中に尋ねる。仮の URL（`#` など）で憶測して埋めない。

## デザインカンプの仕様

デザインカンプは実装サイズの**2倍の解像度**で提出される（Retina 想定の一般的な入稿仕様）。

- **PC**: 実装幅は 640px。デザインカンプは **1280px**（2倍）で提出する。PC のコーディング（`@media (width >= 640px)` 側）は**ピクセルパーフェクト**で行う。カンプ上で測定した px 値を**2で割った値**をそのまま使う（例: カンプ上で 40px の余白 → 実装は 20px）。
- **SP**: 実装の基準幅は 375px。デザインカンプは **750px**（2倍）で提出する。320px〜640px の範囲はブレークポイントで区切らず、ウィンドウ幅に応じて**成り行きで比例縮小/拡大**させる。640px 以上は PC レイアウトに切り替わる。
- SP のフルードスケーリングの実装方法（750px カンプの測定値をそのまま使う `vw` 比例値への変換）は @css-architecture.md を参照。

## デザインカンプの受け渡しと計測

デザインカンプ（Photoshop などからの書き出しファイル）は、画像アセットと同様に**チャット添付ではなくファイルパスで受け渡す**。理由は保存のためではなく、**正確な計測のため**。

エージェントはチャットに貼られた画像を目視で確認することはできるが、目視での寸法・色の読み取りには誤差が出やすい（特に縦に長いページ全体のカンプや、正確な hex カラーコード）。ファイルパスが分かれば、Bash 上で画像処理スクリプト（Python の Pillow、`ImageMagick` の `convert`/`identify` など）を使い、

- 指定座標のピクセル色を実測して正確な hex 値を取得する
- 要素の境界や余白をピクセル単位で計測する
- 画像全体のサイズ（1280px / 750px になっているか）を確認する

といった**目視によらない正確な計測**ができる。実装前にこれらの値を計測してから CSS に反映することで、色・サイズのズレを大きく減らせる。

デザインカンプ自体はリポジトリに**コミットしない**。計測に使うだけで、`dist/images/` への配置やリポジトリへの保存は不要（`dist/images/` に置くのは納品用の画像アセットのみ）。

## デザインカンプ再現の精度を上げるルール

`/coding` の結果がデザインカンプと大きくズレる（商品画像のサイズが違う、ボタンの色が違う、バナーのサイズが違う等）場合、主な原因は次のいずれかであることが多い。実装時・レビュー時ともに以下を確認する。

- **目分量で測らない**: 「デザインカンプの受け渡しと計測」の手順で、色・寸法をスクリプトで実測してから実装する。画像に「Multiply coordinates by X to map to original image」のような実寸換算の倍率が表示されている場合はその倍率も使えるが、可能な限りスクリプトによる実測を優先する。
- **テンプレートのダミー値を残さない**: `00000html/` を複製した直後の `dist/styles/style.css` には、色・余白・フォントサイズなどが見本用のダミー値のまま入っている（例: ボタンの背景色、セクションの背景色）。`Blocks` セクション・`Pages — project` セクションの数値・配色は、このダミー値をそのまま使わず、必ず今回のデザインカンプから実測した値に置き換える。特に配色（背景色・文字色・ボタン色など）をテンプレートのまま残さないこと。
- **サイト共通 CSS の影響を疑う**: `<head>` 内で読み込まれる jQuery Mobile / Bootstrap スコープ / `reset.css` / `properties.css` / `main.css` / `layout.css` / `module.css` / `style--common-sp-and-pc.css` / `style--pc.css` / `style--sp.css` は CMS 側の共通 CSS で、こちらから変更できない。デザインカンプと差がある要素は、ブラウザの開発者ツールで Computed スタイルを確認し、これらの共通 CSS に起因する意図しないスタイル（余白・行間・リンク色・リスト記号など）が当たっていないか調べる。当たっている場合は、`.p{id}` 配下に詳細度の高い上書きルールを `Foundation` セクションへ追加して打ち消す（既存の前例: `.bootstrap-v3-3-7--scope .p{id} a:focus`）。

## 編集範囲

コーディングするのは対象ディレクトリの `dist/{id}.html` のうち、**`<!-- 商品概要 -->` と `<!--//商品概要 -->` の間のみ**。この範囲外（`.pjt--common` 内のフッター注意文言を除く）は明示的な指示がない限り変更しない。

必要な CSS の追加は @css-architecture.md の区分に従う（`dist/styles/style.css` を直接編集し、使い回せる UI は `Blocks` セクション、この案件だけの組み立ては `Pages — project` セクションに書く）。ブレークポイント・クラス命名は `00000html/`（テンプレート）を参照する。具体的には:

- コンテナは `max-width: 640px` を土台にしたモバイルファースト。PC 用の分岐は `pc:p{id}-hidden` / `pc:p{id}-inline` のような `pc:` プレフィックス付きユーティリティ、または `@media (width >= 640px)` を使う。
- クラス名は `p{id}-{block}` / `p{id}-{block}__{element}` / `--{modifier}` / `is-*` の Modern BEM 規則に従う（詳細は @css-architecture.md）。

## フッター注意文言の扱い

ヒアリングした選択に応じて `.pjt--common` 内の 4 パターンのブロックを次のように処理する。

- いずれか 1 つを選択した場合: 選んだブロックのみ残し、残り 3 つの HTML ブロックは削除する（コメントアウトではなく削除）。誤って不要な注意文言が公開されるのを防ぐため。
- 「不要」を選択した場合: 4 つのブロックすべてを削除する。

## アコーディオンUIの扱い

ヒアリングした回答に応じて、`p{id}-accordion-details`（`dist/styles/style.css` の `Blocks — accordion` セクションと `dist/scripts/accordion.2.js`）の組み込みを次のように処理する。

- 「使う」場合: `<details class="p{id}-accordion-details">` のマークアップを商品概要エリア内に追加し、`accordion.2.js` の `<script>` タグ（ローカル / CDN 切り替えコメント付き、@project-workflow.md 参照）を HTML に含める。
- 「使わない」場合: アコーディオンのマークアップを追加しない。`accordion.2.js` の `<script>` タグ（ローカル行・CDN コメント行の両方）も HTML に含めない。使わない JS を読み込んだまま残さない。

## 画像アセットの受け渡し

エージェントはチャットに貼られた画像を**見て内容を把握する**ことはできるが、その画像データをそのままファイルとして書き出すことはできない（テキストしか書き出せない）。そのため、`dist/images/` に配置が必要な**納品用の画像アセット**は、次の手順で受け渡す。

1. ユーザーが画像ファイルを PC 上の任意の場所（プロジェクトフォルダ内、ダウンロードフォルダなど）に実体として保存する。
2. そのファイルパス（またはファイル名。プロジェクトフォルダ内に置いた場合）をエージェントに伝える。
3. エージェントはそのパスから `dist/images/` へコピー・リネームする（命名規則は次項）。

**デザインカンプ**も同様にファイルパスで受け渡すが、目的は保存ではなく正確な計測のため（詳細は「デザインカンプの受け渡しと計測」）。

## 画像アセットの命名

既存の運用に合わせ、`dist/images/` に配置するファイル名は `{id}-{意味のある名前}[--pc|--sp][.バージョン番号].{拡張子}` の形式を踏襲する（例: `15066-figure-1--pc.webp`、`15066-kv.4.webp`）。SP/PC で画像を出し分ける場合のみ `--sp` / `--pc` を付ける。

## SP/PC 画像の出し分け

スマホ用とPC用で画像を出し分ける場合は `<img>` の `src` を JS 等で切り替えず、`<picture>` タグを使う。ブレークポイントは `00000html/` に合わせて `640px` とする。

```html
<picture>
  <source media="(min-width: 640px)" srcset="./images/{id}-{名前}--pc.webp">
  <img src="./images/{id}-{名前}--sp.webp" alt="...">
</picture>
```

`<img>` にはフォールバックとして SP 用画像を指定する（`<picture>` 未対応環境や `<source>` が一つも一致しない場合に使われるため）。`alt` は `<img>` 側にのみ付ける。

## 実装後の確認

- Live Server でスマホ幅・PC 幅（640px 境界）の両方を目視確認する（ビルド・監視ステップはないため、保存すれば即反映される）。
- PC（640px 幅）は、1280px のデザインカンプを2分の1に換算した値とピクセル単位で一致しているか人がレビューする。
- SP は 320px・375px・640px 付近の複数幅で、比例縮小/拡大が破綻していないか（文字や画像がはみ出さないか）を確認する。
